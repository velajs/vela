Match Nest's wildcard middleware targets with Nest's meaning. `forRoutes()` and `exclude()` targets now compile to anchored regular expressions owned by Vela instead of a Hono router, so a wildcard backtracks onto whatever follows it. `cats/*path` (Nest 11) and `cats/(.*)` match one or more segments below `/cats` but not `/cats` itself, so `exclude('users/*id')` still runs the middleware on `/users`. A mid-path wildcard matches one or more segments in its place: `files/*path/:id` runs on `/files/a/b` and `/files/a/b/c`, and `users/*id/admin` covers `/users/1/admin/settings`. A trailing `cats/{*splat}` also matches `/cats`, as in Nest. Literal segments are escaped, so `v1.0` matches only `/v1.0`. Every wildcard Vela generates, including the paths beneath a `forRoutes()` target, also matches line terminators, since Hono decodes `%0A`, `%0D`, `%E2%80%A8` and `%E2%80%A9` into the request path that a `:id` route accepts. An `exclude(':id?')` target also matches the root path, as Hono's optional parameter does. These targets previously never matched, so the middleware silently skipped the routes they named. The startup check of relative targets uses the same matcher and accepts a target only when some concrete path matches both it and a registered route.

**Behavior change:** a `forRoutes()` or `exclude()` path that uses other group, optional-segment or named-wildcard syntax, such as `:id(\d+)`, `users{/:id}`, `ab*cd` or a `{*splat}` before the last segment, now throws at route build instead of silently matching nothing. Hono's regex-constrained parameters such as `:id{[0-9]+}` are still accepted; use them for a constrained segment. A `:` inside a literal segment, such as `files/abc:name`, which Hono's routers read differently, and a target with more than one wildcard that spans segments, such as `files/*a/*b` or `files/*a/*`, whose matching would slow down on long paths, also throw at route build.
