# Internationalization

Import `I18nModule` from `@velajs/vela/i18n` and install the optional
`intl-messageformat` peer dependency. Configure locale detection once, then
contribute messages from the feature modules that own them:

```ts
import { Inject, Injectable, Module } from '@velajs/vela';
import { I18nModule, I18nService } from '@velajs/vela/i18n';

@Module({
  imports: [
    I18nModule.forFeature({
      en: { notifications: { welcome: 'Hello, {name}!' } },
      pt: { notifications: { welcome: 'Olá, {name}!' } },
    }),
  ],
})
class NotificationsModule {}

@Module({
  imports: [
    I18nModule.forRoot({
      isGlobal: true,
      defaultLocale: 'en',
      fallbackLocale: 'en',
      locales: ['en', 'pt'],
    }),
    NotificationsModule,
  ],
})
class ApplicationModule {}

@Injectable()
class WelcomeMessage {
  constructor(@Inject(I18nService) private readonly i18n: I18nService) {}

  text(name: string) {
    return this.i18n.t('notifications.welcome', { name });
  }
}
```

Register `WelcomeMessage` as an application provider. `I18nService` reads the
request's locale, and providers that inject it inherit request scope. The module
installs locale middleware; the default detector reads `Accept-Language`.
`detection.strategy` also accepts `query` and `cookie`, with `lookupKey` defaulting
to `locale`. `detection.enabled: false` always uses the default locale.

`forFeature(messages)` snapshots its message tree. Only feature modules imported
into the application's module graph contribute messages. Calling `forFeature`
without importing its result has no effect, and separate applications never
share catalogs. Messages are deep-merged in module registration order: later
imports override earlier leaves. Repeated identical trees contribute once at
their first import position, including repeated imports through shared modules.

The loader compiles ICU messages lazily. A missing translation falls back to
`fallbackLocale`; a key missing from both locales is returned unchanged.

Replace previous `I18nModule.registerMessages(messages)` calls with
`I18nModule.forFeature(messages)`. Static `MessageRegistry.addMessages()` and
`MessageRegistry.reset()` no longer exist; catalog ownership follows module
imports and does not require a process-wide registry reset.
