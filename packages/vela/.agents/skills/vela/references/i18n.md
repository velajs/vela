# Internationalization (`@velajs/vela/i18n`)

Locale detection + ICU message formatting on the **subpath** `@velajs/vela/i18n`. Translation formatting uses `intl-messageformat`, an **optional peer dependency** — install it when you use i18n (`pnpm add intl-messageformat`). Because the subpath imports it statically, importing `@velajs/vela/i18n` requires the package to be present.

## Setup

```ts
import { I18nModule } from '@velajs/vela/i18n';

const messages = {
  en: { greeting: 'Hello, {name}!', items: '{count, plural, one {# item} other {# items}}' },
  fr: { greeting: 'Bonjour, {name} !' },
};

@Module({
  imports: [
    I18nModule.forRoot({ defaultLocale: 'en', locales: ['en', 'fr'] }),
    I18nModule.forFeature(messages),
  ],
  controllers: [HomeController],
})
class AppModule {}
```

`I18nModuleOptions`:

| Field | Default | Notes |
|---|---|---|
| `defaultLocale` | `'en'` | used when detection is off or no match |
| `fallbackLocale` | = `defaultLocale` | per-key fallback for missing translations |
| `locales` | `['en']` | supported list; unlisted request locales fall back |
| `detection` | see below | `{ enabled?, strategy?, lookupKey? }` |

`detection.strategy` is `'header'` (default, reads `Accept-Language`), `'query'` (reads `?locale=`), or `'cookie'`. `lookupKey` (default `'locale'`) is the query/cookie name. `detection.enabled` defaults `true`. `forRootAsync` is also available. `forFeature(messages)` contributes `{ [locale]: {...} }` to the importing application. Unimported features contribute nothing; repeated imports deduplicate and later contributions override earlier leaves. Each application owns its catalog.

## Translating

`I18nService` is **request-scoped** — inject it in a controller/request-scoped provider and call `t`:

```ts
import { I18nService } from '@velajs/vela/i18n';

@Controller('/')
class HomeController {
  constructor(private readonly i18n: I18nService) {}

  @Get()
  hello() {
    return { message: this.i18n.t('greeting', { name: 'Ada' }) };  // dot-path key + ICU params
  }
}
```

`I18nService` API: `t(key, params?)` (dot-path key, ICU `{name}` / plural params) and `getLocale()`. The locale is resolved per request by the middleware and is read-only — there is no `setLocale`. A missing key falls back to `fallbackLocale`, then returns the raw key.

## Middleware

`I18nModule` registers a global middleware (`APP_MIDDLEWARE`) that detects the request locale (per the `detection` strategy — parsing `Accept-Language` q-values, the query param, or the cookie) and stashes it on the request context, where `I18nService.getLocale()` reads it. Region codes fall back (`en-US` → `en`). No extra wiring needed beyond `forRoot`.
